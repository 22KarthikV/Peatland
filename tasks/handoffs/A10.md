**Decisions / gotchas:**
- Race safety comes from the single conditional UPDATE: under READ COMMITTED a concurrent heartbeat UPDATE makes Postgres re-evaluate the WHERE on the new row version, so a run that just heartbeated is skipped.
- Terminal rows are never touched (`status = 'running'` filter). `queued` runs are out of scope, as requested. The DLQ-arrival reaper (queue.md item 5) is not implemented.
- The worker's own takeover threshold (`stale_after`, 300 s) is below the reaper timeout (900 s), so a redelivered message takes over a dead run before the reaper fails it; the reaper catches runs whose message is gone or is not redelivered. The reaper runs only between messages, in the poll loop, so a worker blocked in a long step does not reap while busy; with one worker a lost run is reaped on the next poll after the restart. With several workers any idle one reaps.
- The state-machine trigger forbids `queued -> succeeded`, so tests move rows through `running` first.
- `test_reaper.py` imports fixtures from `test_worker`/`test_db` and uses a file-level `# ruff: noqa: F811`; `mypy` on the tests dir cannot resolve those imports (not part of the gate).
