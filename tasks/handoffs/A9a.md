**Changed:**
- New `api/src/api/steps.py`, class `WorkerSteps(session_factory, s3, *, data_bucket, artifacts_bucket, runner=run_pipeline, workdir, code)`. The worker still runs two steps (`pipeline`, `inference`); they dispatch on `message.kind`:
  - `pipeline_step` (kind=pipeline): reads `sites.boundary_uri` from S3 and checks it against `boundary_sha256` (`step_failed` on mismatch or missing). For each window it builds a `RunConfig` (cloud threshold = `params.max_cloud_cover_pct`, default 40) and calls `pipeline.runner.run_pipeline(..., s3=client)`, which skips the run if the key is already stored. It then reads the stored sidecar and upserts `composites` (`ON CONFLICT (site_id, year, season) ... WHERE key differs`). `NoUsableScenesError` -> `StepError('no_usable_scenes')` with detail `{window, max_cloud_cover_pct}`; a scene that is not BOA-corrected -> `step_failed`. Returns `{composite_ids}`.
  - `inference_step` (kind=pipeline): only model name `ndvi-baseline` is accepted; any other model fails with `step_failed`, detail `{model}`. For each composite it computes the classification idempotency key (C2 s.6; parameters = rules + window 512 / overlap 128, inputs = [composite key]). If the stored sidecar key matches, it reuses the row, or rebuilds the row from the stored COG. Otherwise it downloads the composite, runs `ml.infer.predict_cog(src, dst, ndvi_baseline_model())`, uploads the COG and then the sidecar (`classifications/<site>/<year>/<season>/ndvi-baseline-1.0.0.tif` + `.json`), and upserts `classifications` with `class_areas_ha` (every class id, nodata excluded). Returns `{classification_ids, change_id: null}`.
  - `pipeline_step` (kind=change) is a no-op. `inference_step` (kind=change) looks up the composite and classification for both windows and the run's model (`classification_missing` with the same detail shape as the API). It checks that from < to, then runs `ml.change.detect_change`, uploads `changes/<site>/<y1>-<s1>__<y2>-<s2>/<model>-<ver>.tif` + sidecar (with `change_pair`), writes `exports/<run_id>/stats.csv`, and upserts `changes`. The `stats` value is converted from the ml ChangeStats to the db-schema shape (`from_class_id`/`to_class_id`, `class_areas_ha.{from,to}`). It returns `{composite_ids: [], classification_ids: [], change_id}`, which matches the outputs the API presets.
  - Every step appends JSONL events (`step_start`, the pipeline runner's events, `skipped`/`uploaded`, `step_done`/`step_failed`/`step_crashed`) to `peatwatch-artifacts/runs/<run_id>/log.jsonl`. This is best effort.
  - `register_baseline()` inserts the `ndvi-baseline` / `1.0.0` model row if it is missing (`is_default = true` only when no default exists, `ON CONFLICT DO NOTHING`). It also uploads `models/ndvi-baseline/1.0.0/model-card.json` with the rule thresholds.
  - S3 objects are downloaded to a temp dir with boto3 and read locally, so there is no /vsis3 or GDAL S3 configuration for products. `s3_client_from_settings` uses path-style addressing when an endpoint is set.

**Decisions / gotchas:**
- **Named seasons:** `run_pipeline` always writes the custom-window key (`w<start>-<end>`); it takes no season. A window the API resolves to `spring`/`summer`/... is therefore stored and indexed under its `w...` token, taken from the sidecar, and the worker logs a warning. A later `POST /changes` that asks for `spring` will get `classification_missing`. The demo windows (ADR 0003) are custom windows, so CP3 is not affected. Fixing it needs a pipeline change (below).
- Model name `ndvi-baseline`, version `1.0.0`. There is no weights file, so `artifact_uri` = `model_card_uri` = `.../model-card.json`. This deviates from the `model.onnx` example in db-schema.md. The baseline becomes the default model only if no default exists.
- `code` (sidecar `versions.code`, hashed into keys) comes from env `PEATWATCH_CODE_VERSION`, else `git rev-parse`, else `0000000`. The image has no git, so all keys use `0000000` unless the env is set (the pipeline's composite keys behave the same).
- No STAC items (`.stac.json`) are written for classifications or changes. The pipeline runner does not write them for composites either.
- `class_areas_ha` and change stats count every non-nodata pixel of the raster grid. Whether pixels outside the boundary polygon are nodata depends on the pipeline composite (grid = boundary bbox).
- `AWS_NO_SIGN_REQUEST=YES` is for GDAL (P8's live run needed it). I believe botocore does not read it, so boto3 should still sign with the env credentials, but LocalStack accepts unsigned requests, so this is unverified. Recheck before deploying to real AWS.
- The change run's `progress.step` reads `pipeline` then `inference`, because the worker's step names are fixed.
