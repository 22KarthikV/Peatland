# A5 handoff: runs endpoints and enqueue

Done: `POST /sites/{id}/runs` (202 new, 200 identical active run, `Location` on 202) and `GET /runs/{id}`.
Files: `api/src/api/routes/runs.py`, `queue.py`, `schemas.py` (DateRange, RunCreate, ModelRef, Run), `main.py`, `api/tests/test_runs.py`.

## Behaviour
- Queue: `JobQueue` protocol; `SqsJobQueue` (boto3, `AWS_ENDPOINT_URL`, queue name from `settings.queue_name`); `InMemoryJobQueue` fake. Inject with `app.dependency_overrides[get_queue]`.
- Order: row inserted and committed as `queued`, then message sent. Send failure sets the run `failed` (error `enqueue_failed`, finished_at) and returns 503 `enqueue_failed` with `detail.run_id`. 503 is not listed in openapi.yaml; coordinator may want to add it.
- Idempotency key: SHA-256 of canonical JSON `{kind:"pipeline", site:<slug>, boundary_sha256, params, model:"<name>-<version>"}`. The contract does not say whether `site`/`model` are slug/string or objects; I chose slug and the `name-version` string. Windows are sorted and de-duplicated and whole-number cloud thresholds become ints, so equivalent requests share a key. The fixture key cannot be reproduced (its boundary hash is not in the fixtures). Race on the partial unique index falls back to the existing run (200).
- Window to season: exact meteorological seasons and Jan 1-Dec 31 (`annual`) map to tokens (winter year = December's year); anything else is `w<YYYYMMDD>-<YYYYMMDD>` with year = start year. Years outside 2015-2100 give 422.
- Model: `model` omitted uses `is_default`; none registered or unknown gives 422. `log_uri` is set at creation.
- Rate limit: the router uses `enforce_rate_limit`; the 10/min job limit applies to this POST (tested).

## boundary.geojson upload (not implemented; needed)
`POST /sites` stores `boundary_uri = s3://<data_bucket>/sites/<slug>/boundary.geojson` and `boundary_sha256` = SHA-256 of `json.dumps(boundary, separators=(",",":"), sort_keys=True)` of the stored MultiPolygon, but never writes the object, so the worker/pipeline cannot read it. Needed: in `create_site`, after the DB flush, `put_object` exactly those bytes (same serialization, so the hash matches) to that key via boto3 behind an interface like `queue.py` (real + in-memory fake, `AWS_ENDPOINT_URL`), inside the same failure handling (roll back the site if the upload fails, or upload before commit). Add a localstack test and a check that sha256(object bytes) == `sites.boundary_sha256`.
