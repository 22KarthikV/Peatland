# A6 handoff: worker and boundary upload

Done: queue worker (`api/src/api/worker.py`, `python -m api.worker`, `api/Dockerfile.worker`), consumer side of `queue.py`, object store (`api/src/api/storage.py`), `POST /sites` boundary upload.

## Worker
- `Worker(consumer, session_factory, pipeline_step, inference_step, ...)`. Steps are `Callable[[StepContext], Mapping]`; `StepContext(run_id, site_id, message, outputs-so-far)`. Returned dicts are merged into `runs.outputs`. `StepError(code, message, detail)` is a handled failure. `main()` wires placeholder steps that raise `StepError("step_failed", "... not wired")`; replace with the real ones after CP2.
- Per message: JSON + `queue.schema.json` validation (path from env `QUEUE_SCHEMA_PATH`, default repo `contracts/`; Dockerfile.worker copies it), then DB check that run/site (id and slug)/model (name and version) match; then claim `queued -> running` (CAS). Zero rows: takeover only if `running` with `heartbeat_at` older than `stale_after` (300 s); otherwise delete the message (terminal, cancelled, or live on another worker).
- Heartbeat thread (60 s) updates `heartbeat_at` and extends visibility to 900 s, using its own session. Progress is `{step, done, total}`. Status is re-read between steps; `cancelled` stops the run and deletes the message.
- Handled failure: run `failed` with `{code, message, detail}`, message deleted. Success: `succeeded` with outputs, message deleted.
- Poison (bad JSON, schema violation, unknown run, site or model mismatch): not deleted; run marked `failed`/`step_failed` when `run_id` is readable.
- Unexpected exception (crash path): message not deleted, run stays `running`, retried after the visibility timeout via takeover. On the 3rd receive the run is marked `failed`/`step_failed` (the message then goes to the DLQ). This is my reading of queue.md items 3 and 4. The reaper for stale heartbeats and DLQ arrival (`worker_lost`, item 5) is not part of A6.
- `queue.py`: `JobConsumer` protocol (`receive/delete/extend_visibility`, `QueueMessage`), implemented by `SqsJobQueue` and `InMemoryJobQueue` (which also simulates visibility expiry and the DLQ after 3 receives, plus `send_raw`).

## POST /sites upload
`storage.put(settings.data_bucket, key, bytes, "application/geo+json")` with exactly the hashed bytes, after the DB flush and before commit; upload failure rolls back and returns 503 `storage_unavailable` (not in openapi.yaml; coordinator may add). Dependency `get_storage` (override in tests; `app.state.object_store`). A test checks that SHA-256 of the stored object equals `sites.boundary_sha256`. Not run against LocalStack; bucket `peatwatch-data` must exist there.
